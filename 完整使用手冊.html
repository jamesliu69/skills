工程工作流指南

適用於 Codex、Claude Code 與支援 Agent Skills 標準的程式代理。這份手冊整理安裝、呼叫方式、完整開發流程、41 個 Skills，以及 C# .NET Framework 4.8／WinForms 自動化機台專案的實務用法。

專案定位

不是「大量生碼工具」，而是可組合的工程紀律。

對齊需求

以逐題訪談、領域語言與 ADR，降低 Agent 誤解需求的風險。

建立回饋迴路

透過型別檢查、測試、可重現命令與 Code Review，讓 Agent 看得到執行結果。

控制複雜度

以深模組、測試 seam、垂直切片與工單依賴，避免快速累積技術債。

這套方法的核心是：保留工程師的控制權。Skill 只規範處理流程，不取代你對需求、架構、風險與驗證方式的決策。

安裝與初始化

每個 Repository 先完成一次設定。

Codex、Claude Code 或其他 Agent Skills 工具

npx skills@latest add mattpocock/skills
全域安裝位置：Codex、Claude、OpenCode、Copilot、Gemini 的 Matt skills 會同步到各自的全域 skills 目錄。更新後請重新啟動工具以清除 skill metadata 快取。

兩種呼叫模式

差異在誰能啟動 Skill。

User-invoked

必須由使用者手動輸入，例如 /to-spec、/implement。適合負責流程編排，避免每輪都增加模型上下文。

Model-invoked

模型可依任務自動選用，也可由其他 Skill 呼叫，例如 /tdd、/diagnosing-bugs、/code-review。

依工作類型選擇 Skill

快速決策表。

工作需求建議 Skill判斷重點
Matt-ask-matt呼叫：/ask-matt詢問哪個 skill 或流程適合目前情境，作為此儲存庫 skills 的路由器。
Matt-batch-grill-me呼叫：/batch-grill-me每回合一次詢問所有關鍵前沿問題的密集訪談。
Matt-claude-handoff呼叫：/claude-handoff將目前對話交接給立即接手工作的全新背景代理。
Matt-code-review呼叫：/code-review沿著固定起點（commit、branch、tag 或 merge-base）檢查變更，分別從標準（是否遵循儲存庫記錄的編碼標準）與規格（是否符合來源 issue／PRD）兩個面向審查。平行執行兩項審查代理，並並列回報結果。當使用者想審查分支、PR、進行中的變更，或要求「審查自 X 以來的變更」時使用。
Matt-codebase-design呼叫：/codebase-design提供設計深層模組的共同詞彙。當使用者想設計或改善模組介面、尋找深化機會、決定接縫位置、讓程式碼更容易測試或讓 AI 更容易導覽，或其他 skill 需要深層模組詞彙時使用。
Matt-design-an-interface呼叫：/design-an-interface使用平行子代理為模組產生多個截然不同的介面設計。當使用者想設計 API、探索介面選項、比較模組形狀，或提到「設計兩次」時使用。
Matt-diagnosing-bugs呼叫：/diagnosing-bugs針對困難錯誤與效能退化的診斷迴圈。當使用者說「診斷」或「除錯」，或回報程式碼損壞、拋出錯誤、失敗或變慢時使用。
Matt-domain-modeling呼叫：/domain-modeling建立並精煉專案的領域模型。當使用者想確定領域術語或通用語言、記錄架構決策，或其他 skill 需要維護領域模型時使用。
Matt-edit-article呼叫：/edit-article透過重組段落、改善清晰度與精簡文字來編輯及改善文章。當使用者想編輯、修訂或改善文章草稿時使用。
Matt-git-guardrails-claude-code呼叫：/git-guardrails-claude-code設定 Claude Code hooks，在危險的 git 指令執行前阻擋它們，例如 push、reset --hard、clean、branch -D 等。當使用者想防止破壞性 git 操作、加入 git 安全 hooks，或阻擋 Claude Code 中的 git push／reset 時使用。
Matt-grill-me呼叫：/grill-me透過密集訪談磨利計畫或設計。
Matt-grill-with-docs呼叫：/grill-with-docs透過逐步追問來磨利計畫或設計，並在過程中建立文件（ADR 與詞彙表）。
Matt-grilling呼叫：/grilling針對計畫、決策或想法對使用者進行密集追問。當使用者想壓力測試想法，或使用任何 grill 觸發詞時使用。
Matt-handoff呼叫：/handoff將目前對話壓縮成交接文件，供另一個代理接續工作。
Matt-implement呼叫：/implement根據規格或一組 tickets 實作工作項目。
Matt-improve-codebase-architecture呼叫：/improve-codebase-architecture掃描程式碼庫以尋找深化機會，產生視覺化 HTML 報告，然後針對選定項目進行追問。
Matt-loop-me呼叫：/loop-me針對想建立的工作流程規格，對使用者進行密集追問。
Matt-migrate-to-shoehorn呼叫：/migrate-to-shoehorn將測試檔案從 `as` 型別斷言遷移至 @total-typescript/shoehorn。當使用者提到 shoehorn、想在測試中取代 `as`，或需要部分測試資料時使用。
Matt-obsidian-vault呼叫：/obsidian-vault使用 wikilinks 與索引筆記搜尋、建立及管理 Obsidian vault 中的筆記。當使用者想尋找、建立或整理 Obsidian 筆記時使用。
Matt-prototype呼叫：/prototype建立一次性原型以回答設計問題。當使用者想確認狀態模型或邏輯是否合理，或探索使用者介面外觀時使用。
Matt-qa呼叫：/qa互動式 QA 工作階段：使用者以對話方式回報錯誤或問題，代理人在背景探索程式碼庫以取得上下文與領域語言，並建立 GitHub issues。當使用者想回報錯誤、進行 QA、建立 issues，或提到「QA 工作階段」時使用。
Matt-request-refactor-plan呼叫：/request-refactor-plan透過使用者訪談建立包含微小提交的詳細重構計畫，然後將其建立為 GitHub issue。當使用者想規劃重構、建立重構 RFC，或將重構拆成安全的漸進步驟時使用。
Matt-research呼叫：/research針對問題調查高可信度的一手來源，並將研究結果以 Markdown 檔案記錄在儲存庫中。當使用者想研究主題、蒐集文件或 API 事實，或委派資料查找工作時使用。
Matt-resolving-merge-conflicts呼叫：/resolving-merge-conflicts當需要解決進行中的 git merge 或 rebase 衝突時使用。
Matt-scaffold-exercises呼叫：/scaffold-exercises建立包含章節、題目、解答與解說的練習目錄結構，並通過 linting。當使用者想建立練習骨架、建立練習 stub，或設定課程章節時使用。
Matt-setup-matt-pocock-skills呼叫：/setup-matt-pocock-skills設定此儲存庫的 engineering skills，包括 issue tracker、triage 標籤詞彙與領域文件配置。第一次使用其他 engineering skills 前執行一次。
Matt-setup-pre-commit呼叫：/setup-pre-commit在目前儲存庫設定搭配 lint-staged（Prettier）的 Husky pre-commit hooks、型別檢查與測試。當使用者想設定 pre-commit hooks、Husky、lint-staged，或提交時的格式化／型別檢查／測試時使用。
Matt-setup-ts-deep-modules呼叫：/setup-ts-deep-modules將 dependency-cruiser 接入 TypeScript 儲存庫，使每個套件成為深層模組：實作隱藏在子資料夾，只能透過入口檔案存取。由使用者主動觸發。
Matt-tdd呼叫：/tdd測試驅動開發。當使用者想先寫測試來開發功能或修正錯誤、提到「red-green-refactor」，或想建立整合測試時使用。
Matt-teach呼叫：/teach在目前工作區中教導使用者新的 skill 或概念。
Matt-to-questionnaire呼叫：/to-questionnaire將無法完整回答的決策轉換成供其他人填寫的問卷。
Matt-to-spec呼叫：/to-spec將目前對話整理成規格，並發佈至專案 issue tracker；不進行訪談，只綜合既有討論內容。
Matt-to-tickets呼叫：/to-tickets將計畫、規格或目前對話拆成一組 tracer-bullet tickets，每張 ticket 宣告其阻塞邊；邊以本機每張 ticket 一個檔案中的文字呈現，或在實際 tracker 中建立原生阻塞連結。
Matt-triage呼叫：/triage讓 issues 與外部 PR 依照 triage 角色的狀態機流轉：分類、驗證、必要時追問，並撰寫可供代理執行的簡報。
Matt-ubiquitous-language呼叫：/ubiquitous-language從目前對話擷取 DDD 風格的通用語言詞彙表，標示歧義並提出標準術語，儲存至 UBIQUITOUS_LANGUAGE.md。當使用者想定義領域術語、建立詞彙表、強化術語、建立通用語言，或提到「領域模型」或「DDD」時使用。
Matt-wayfinder呼叫：/wayfinder規劃超過單一代理工作階段可容納的大型工作，將其拆成 issue tracker 上的共享決策 tickets，逐一解決直到路徑清楚。
Matt-wizard呼叫：/wizard產生互動式 bash wizard，引導人類完成手動程序，例如第三方設定、一次性遷移或 A→B 狀態轉換；wizard 會開啟 URL、擷取值、確認步驟，並寫入 .env 檔案與 GitHub Actions secrets。
Matt-writing-beats呼叫：/writing-beats寫作，探索：將原始素材組合成由段落節拍構成的旅程，並在每個術語被節拍依賴前先建立其基礎。
Matt-writing-fragments呼叫：/writing-fragments寫作，探索：挖掘原始片段，尚不建立結構。
Matt-writing-great-skills呼叫：/writing-great-skills撰寫與編輯優良 skills 的參考資料，涵蓋讓 skill 可預測的詞彙與原則。
Matt-writing-shape呼叫：/writing-shape寫作，發揮：逐段將原始素材塑造成文章。

不同情境的建議用法

情境一：新增自動復歸功能

先釐清狀態、互鎖、允許條件與失敗原因，再拆成可獨立驗證的工單。

/grill-with-docs
/domain-modeling
/to-spec
/to-tickets
/implement

情境二：現場回報難解 Bug

先保留現場證據與重現步驟，不要直接猜測根因；建立可失敗的測試回饋迴路。

/diagnosing-bugs
/research
/tdd
/code-review

情境三：安全互鎖或危險動作

把安全前置條件、禁止條件、超時與人工介入寫成明確政策，再以測試覆蓋每個分支。

/grill-with-docs
/domain-modeling
/to-spec
/tdd
/code-review

情境四：狀態機或 UI 設計不確定

先用拋棄式原型比較狀態模型與操作流程，確認方向後再進入正式實作。

/prototype
/handoff
/to-spec
/implement

情境五：既有程式架構難以維護

先找出複雜度集中處與模組邊界，再制定小步驟重構計畫，避免一次大改。

/improve-codebase-architecture
/request-refactor-plan
/to-tickets
/code-review

情境六：測試不足或回歸風險高

先建立可重現測試，再逐步補上政策介面、狀態轉換與錯誤路徑的測試。

/tdd
/diagnosing-bugs
/implement
/code-review
